# 幽灵引用扫描 v2 — 基准拓扑 + 修正则 + 判定流程

`scripts/scan_ghost_script_refs.py` 扫任务卡/指南书/知识手册/项目文档里引用的 `.py`，与"脚本实际存在处"比对，找幽灵引用。v1 曾把 4 个合法引用误报成"必须修"，v2 修正后**真幽灵 = 0**。

## 目录拓扑：三分法（勿再猜）

多仓项目最常见的情形是"文档在 A、脚本在 B、验证副本在 C"。判定前必须先把这三者的角色钉死：

| 区 | 角色 | 脚本是否存在 |
|---|---|---|
| **开发区**（源） | 脚本/技术的**源头**，编写与迭代都在这里 | ✅ 有 —— **基准** |
| **验证区** | 接收开发区产出、做端到端验证的活库 | ✅ 有（活库，会被更新） |
| **文档区** | 任务卡/指南书/知识手册/协作文档所在 | ❌ 通常**没有** `scripts/`（文档仓为空） |

**基准 = 开发区**。别指向文档区 master（空）或验证区（那是验证副本，不是源）——指错了会把所有引用都判成幽灵。

> 配置方式（开源版通用）：目录不写死在脚本里。命令行 `--docs-root / --zone / --plan-zone / --search-root`，或写进 `mem_rules.json` 的 `content_scans.ghost_scripts.{target, zone_dirs, plan_zone_dirs, search_roots}`。

## v1 三个误报根源（都是扫描器 bug，不是文档问题）

1. **正则误报 URL**：`[A-Za-z0-9_-]+\.py` 会把 `https://download.pytorch.org/...` 里的 `download` + `.py`（`torch` 恰好续成 `download.pytorch` 子串）匹配成 `download.py`。修正则：`.py` 后加负向前瞻 `(?![A-Za-z0-9_.-])` 禁文件名继续字符。
2. **只比对平级目录**：脚本可能合法地待在 `app/ui/`、`webapp/server/`、`src/`、`tools/` 等位置——只看某个 `scripts/` 平级目录会漏报。判定必须全盘搜索。
3. **漏归档区**：被引用的脚本真实存在于归档目录（旧工作区），且文档自己标注了"（归档区 XX 旧工作区）"——非幽灵。

## v2 判定流程（已写进脚本）

- 修正则：`re.compile(r"([A-Za-z0-9_\-]+\.py)(?![A-Za-z0-9_.\-])")`
- 存在性：候选幽灵在 **search roots**（开发区 + 验证区 + 归档区）全盘 `os.walk` 二次搜索，找到即排除（跳过 `.git` / `.venv` / `site-packages` / `node_modules` / `app_bak_*` / `__pycache__`）
- 输出三级：✅ 已解决引用（全盘命中）/ ❌ 真幽灵（全盘无，执行区引用→必须修）/ B 类规划引用（规划文档里的示例/占位，需人工确认）
- 分区语义：`--zone`（执行区：任务卡/指南书/知识手册，引用必须是活的）与 `--plan-zone`（规划区：示例/未来规划，可容忍不存在）
- 正则单测要点：应匹配 `train_mlp.py 训练`、`python scripts/train_eegnet.py`、`(cloud_report.py)`；应不匹配 `download.pytorch.org`、`foo.pyz`、`a.py.bak`

## 结论纪律

- 引用旧扫描/体检结论前**用当前脚本复跑**（同一仓库 v1→v2 结论从"14 个幽灵"→"0 个"）。
- 报告"真幽灵 N 个"前，先确认三个误报源（URL 子串 / 子目录 / 归档区）都已排除。
